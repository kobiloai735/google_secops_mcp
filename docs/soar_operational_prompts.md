# 5 פרומפטים מבצעיים ל‑Google SecOps SOAR

פרומפטים לשימוש עם שרת ה‑MCP של SecOps SOAR (`secops-soar`).
כל פרומפט מנוסח כך שהעבודה מתבצעת **אך ורק בכלי SOAR** (cases, alerts, entities, comments,
insights, priority/assignment), ומייצר ערך חוצה‑מערכות — כלומר קורלציה בין תיקים,
מקורות התראה ואינטגרציות שונות שמזינות את ה‑SOAR, ולא שאילתה בודדת.

לפני כל פרומפט: הרץ פעם אחת `list_cases` מצומצם כדי לוודא חיבור ולתפוס את מבנה השדות בטננט שלך.

---

## 1. תדריך מסירת משמרת (Shift Handover Brief)

**ערך מבצעי:** מחליף 20–30 דקות של חפירה ידנית ב‑Case Queue בתחילת כל משמרת, וחושף תיקים שנתקעו.

```
השתמש רק בכלי ה‑SOAR של SecOps. אל תריץ שאילתות SIEM ישירות.

בנה לי תדריך מסירת משמרת ל‑24 השעות האחרונות:
1. משוך את כל התיקים הפתוחים (list_cases), כולל priority, stage, assignee, זמן פתיחה
   ומקור ההתראה/האינטגרציה.
2. סווג אותם לארבע קבוצות: (א) חדשים שלא נגע בהם אף אחד, (ב) בטיפול פעיל,
   (ג) ממתינים לגורם חיצוני, (ד) תקועים — ללא תגובה או הערה מעל 8 שעות.
3. לכל תיק בקבוצות (א) ו‑(ד) משוך את ההתראות שלו ואת ההערות האחרונות
   וכתוב שורת סיכום אחת: מה קרה, על מי/מה, ומה הצעד הבא הנדרש.
4. סמן חריגות SLA: תיק High/Critical פתוח מעל 4 שעות, או Medium מעל 24 שעות.

פלט: טבלת מסירה ממוינת לפי סיכון (Case ID, כותרת, עדיפות, אחראי, גיל, סטטוס SLA,
צעד הבא), ואחריה שלוש שורות "מה חייב לקרות במשמרת הבאה".
אל תשנה שום תיק — קריאה בלבד.
```

## 2. קורלציית ישויות חוצת‑תיקים (זיהוי קמפיין)

**ערך מבצעי:** חושף שתיקים שנראים בודדים הם למעשה אותו אירוע — המקום שבו SOAR נותן ערך שאף התראה בודדת לא נותנת.

```
השתמש רק בכלי ה‑SOAR של SecOps.

מצא קמפיינים חבויים בין תיקים פתוחים ב‑7 הימים האחרונים:
1. משוך את כל התיקים הפתוחים, ולכל תיק את ההתראות והישויות שלו
   (משתמשים, hostnames, כתובות IP, דומיינים, hashes, כתובות מייל).
2. בנה מפת ישויות: כל ישות שמופיעה ביותר מתיק אחד, כולל רשימת התיקים
   ומקורות ההתראה השונים (EDR, מייל, ענן, זהויות) שבהם הופיעה.
3. דרג כל אשכול לפי: מספר התיקים, מגוון מקורות ההתראה, העדיפות הגבוהה ביותר
   באשכול, וקרבה בזמן.
4. לשלושת האשכולות המובילים הצע השערת תקיפה אחת בשפה פשוטה
   ("אותו משתמש נפרץ ואז ניסה תנועה רוחבית") ואת התיק שראוי לשמש כתיק אב.

פלט: לכל אשכול — ישות מקשרת, רשימת Case IDs, ציר זמן קצר, הערכת ביטחון (גבוה/בינוני/נמוך)
והמלצת מיזוג/הסלמה. אל תמזג ואל תסגור תיקים בעצמך — רק המלץ.
```

## 3. טריאז' והעשרה אוטומטית לתיקים חדשים

**ערך מבצעי:** מוריד את זמן ה‑Time‑to‑Triage; כל תיק מגיע לאנליסט כשהוא כבר מועשר ומתועד.

```
השתמש רק בכלי ה‑SOAR של SecOps.

בצע טריאז' לכל התיקים בעדיפות High/Critical שנפתחו ב‑12 השעות האחרונות:
לכל תיק —
1. משוך את פרטי התיק המלאים, את ההתראות שלו ואת האירועים שמאחורי כל התראה.
2. חלץ את הישויות המרכזיות והרץ עליהן חיפוש ישויות ב‑SOAR: האם הישות מוכרת,
   האם הופיעה בתיקים קודמים, ומה היה הפסק שם (אמיתי / FP).
3. הצלב מול רשימות ההעשרה והאינטגרציות הזמינות בתיק (מודיעין, זהויות, נכסים)
   וקבע פסק ראשוני: True Positive סביר / דורש בירור / False Positive סביר.
4. כתוב הערה מובנית לתיק (post_case_comment) בפורמט:
   מה זוהה | ישויות מעורבות | ממצאי היסטוריה | פסק ראשוני + נימוק | 3 צעדי חקירה מומלצים.
5. אם הראיות חלשות והישות סומנה בעבר כ‑FP — המלץ על הורדת עדיפות, אך אל תשנה
   עדיפות או תסגור תיק ללא אישור מפורש ממני.

פלט: טבלת סיכום (Case ID, פסק, ביטחון, פעולה מומלצת) + אישור אילו הערות נכתבו בפועל.
```

## 4. כריית רעש: מה מציף את ה‑SOC

**ערך מבצעי:** מזהה את מקורות ההתראה שגוזלים את רוב זמן האנליסטים, עם המלצות טיונינג מבוססות נתונים.

```
השתמש רק בכלי ה‑SOAR של SecOps.

נתח את רעש ההתראות ב‑30 הימים האחרונים:
1. משוך את כל התיקים שנסגרו, כולל סיבת סגירה, root cause, עדיפות,
   מקור ההתראה/הכלל שיצר אותם וזמן הפתיחה והסגירה.
2. חשב לכל מקור התראה: כמות תיקים, אחוז סגירה כ‑False Positive,
   זמן טיפול ממוצע, וסך "שעות אנליסט" מבוזבזות (כמות FP × זמן טיפול ממוצע).
3. דרג את 10 המקורות היקרים ביותר לפי שעות מבוזבזות, לא לפי כמות.
4. לכל אחד מחמשת המובילים — משוך 3 תיקים לדוגמה, קרא את הערות הסגירה,
   וזהה את המכנה המשותף (שרת סורק לגיטימי, משתמש שירות, טווח IP פנימי, תהליך מוכר).
5. הצע לכל אחד המלצת טיונינג קונקרטית: מה להוסיף ל‑reference list / allowlist,
   או איזה תנאי לחדד — כולל הערך המדויק לחריגה.

פלט: טבלת דירוג + לכל מקור: סיבת הרעש, המלצת טיונינג מדויקת, וכמה שעות אנליסט
בחודש היא חוסכת. סמן בנפרד כל המלצה שעלולה ליצור נקודת עיוורון, והסבר את הסיכון.
```

## 5. תיק חקירה מלא סביב ישות (משתמש / נכס)

**ערך מבצעי:** מייצר ב‑2 דקות את מה שאנליסט בונה בשעה — ציר זמן מלא של ישות על פני כל התיקים והמקורות.

```
השתמש רק בכלי ה‑SOAR של SecOps.

בנה תיק חקירה מלא עבור הישות: <משתמש / hostname / כתובת IP>.

1. חפש את הישות ב‑SOAR ומשוך את כל התיקים וההתראות שבהם היא מופיעה
   ב‑90 הימים האחרונים — פתוחים וסגורים כאחד.
2. לכל תיק רלוונטי משוך את ההתראות, האירועים שמאחוריהן ואת הערות האנליסטים,
   כולל הפסק שנקבע בסגירה.
3. בנה ציר זמן כרונולוגי אחד: תאריך ושעה, מה קרה, מאיזה מקור/אינטגרציה הגיע,
   אילו ישויות נוספות היו מעורבות, ומה הוחלט בפועל.
4. זהה הסלמה: האם מאופי הפעילות עולה מגמה (מהתראות מדיניות בודדות
   לפעילות חשודה חוזרת), ואילו ישויות נוספות "נדבקו" לישות הזו לאורך הזמן.
5. קבע פסק סופי עם רמת ביטחון, והצע 3 פעולות הכלה מדורגות לפי השפעה על העסק.
6. כתוב את התקציר כהערה בתיק הפתוח והעדכני ביותר של הישות.

פלט: ציר זמן + מפת ישויות מקושרות + פסק והמלצות. אם אין ממצאים — אמור זאת
במפורש ואל תמציא קשרים. פעולות הכלה — המלצה בלבד, לא ביצוע.
```

## עקרונות שחוזרים בכל הפרומפטים

| עיקרון | למה |
|---|---|
| הגבלה מפורשת לכלי SOAR | מונע נדידה לשאילתות SIEM שמחזירות אלפי אירועים גולמיים |
| חלון זמן מוגדר | שומר על תגובה בגודל סביר וקבוע |
| פלט מובנה (טבלה/ציר זמן) | ניתן להדבקה ישירה לתדריך משמרת או לתיק |
| קריאה בלבד כברירת מחדל | שינויי עדיפות, מיזוג וסגירה — רק באישור מפורש |
| "אם אין ממצאים — אמור זאת" | מונע קשרים מומצאים בין תיקים |
